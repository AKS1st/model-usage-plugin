# 模型消耗统计（model-usage-plugin）

DeepSeek Harness（DSH）Web 插件：统计各模型 tokens 消耗并估算费用，显示 API 账户余额。

![设置面板"模型消耗"页签效果](docs/overview-light.png)

<sub>总览页（浅色）。深色主题、模型明细页与配置页见[界面预览](#界面预览)。</sub>

## 功能

- 按模型统计 tokens（区分缓存命中 / 未命中 / 写入）、调用与失败次数，估算费用
- 内置主流模型默认价格（国产模型按人民币、海外模型按美元），首次使用自动套用，可随时修改
- 峰谷定价：每个模型可勾选"峰谷定价"，最多支持两个高峰时段（HH:MM，支持跨零点），
  两个高峰时段共用同一组高峰价；每个时段可单独指定 **时区**（默认 UTC）与是否
  **仅周一至周五**生效；高峰期 token 按高峰价计费，非高峰期按正常价计费（高峰价留空则沿用正常价）
- DeepSeek 默认价按官方 **2026-09-10 V4.1 定价**预置：官方模型名为 `deepseek-flash`
  （DeepSeek-V4.1-Flash），空闲价 ¥1 / ¥4 / ¥0.02（缓存未命中 / 输出 / 缓存命中），
  高峰价为 2 倍（¥2 / ¥8 / ¥0.04），窗口为 **UTC 周一至周五 01:00–04:00 与 06:00–10:00**，
  周末全天按空闲价。已退役的 `deepseek-v4-flash` / `deepseek-v4-flash-vision-exp` /
  `deepseek-v4-pro` 等 id 仍可调用，但已（或将）路由到 V4.1 Flash 并按 Flash 价计费，
  因此默认预设按同一口径预置
- 模型 id 归一会自动识别 provider 前缀、日期后缀、`:batch` 变体与上述 DeepSeek 旧 id，
  使其命中同一条价格，不会出现"正在用的模型没有价格"
- 启动迁移：旧数据的默认价与高峰窗口会自动升级到当前官方口径；尊重用户自定义——
  明确关掉峰谷开关的价格不会被重新打开，自定义单价也不会被覆盖
- **有统计就必须有价**：启动时会为"有用量但价格表里没有"的模型补上默认预设价
  （用户显式移除过的除外）。`record()` 的自动套用只在首次调用时触发，若某模型首次调用时
  价格表里还没有它（例如 `deepseek-flash` 在旧版本里不存在），之后永远不会补上——
  界面上就会出现"有调用量但没有价格" 
- 汇率换算：费用统一按目标货币展示（默认人民币）。汇率成功获取后连同时间戳缓存到数据文件，
  无缓存时启动自动刷新一次；打开设置页时缓存不超过一周不自动刷新（需手动点击"更新汇率"），
  无缓存或超过一周自动刷新一次
- 查询 DeepSeek 账户余额，页面顶部大字展示总 Token 与账户余额
- **图表呈现**（纯 SVG，不引入图表库；配色从 harness 设计令牌派生，深/浅主题自动跟随）：
  - **用量趋势卡**：按天 / 按小时切换的堆叠柱，**默认按费用口径**（可切 Tokens）；
    柱内按模型堆叠，悬停给出该时段的逐模型明细
  - **每模型费用 + 占比**：卡片主数字是费用，紧跟一行费用占比条与百分数；
    模型列表与趋势卡图例**共用同一排序（按费用降序）**，避免两处给出不同的"第一名"
  - **每模型 token 构成条**：未命中 / 缓存命中 / 缓存写入 / 输出四档占比
  - token 明细与价格配置按需展开，默认不铺开

  刻意**没有**用环形图呈现占比：套餐里往往一个模型占绝大多数 token，环形图会退化成
  一个整圆，等于没画；而且按 token 排会把"调用次数少但单价高"的模型藏起来——那恰恰
  是最该优化钱的地方。费用占比进到每一行里，比单独一张图更贴近"我该动谁"。
  - **缓存命中率**：总 Token 卡下方直接给出被计费提示词中的缓存命中比例
  - **效率卡**：把"花了多少"推进到"花得值不值"——工具调用数 · 失败率 · 每调用均价 ·
    每调用 Token · 高频工具
  - **工具口径**：趋势卡在费用 / Tokens 之外多一个「工具」口径，可对比"某天贵是因为
    模型啰嗦还是工具循环太多" 
- 时间台账：从本版本起按天（保留 120 天）与按小时（保留 26 小时）增量聚合，
  不做历史回填；快照只下发最近 45 天，其中最近 32 天带逐模型明细
- 设置面板"模型消耗"页签；"仅显示已调用模型"可隐藏未使用过的模型

### 页面结构（三个子页面）

主页只放宏观统计，**高度不随模型数增长**；明细与配置各自成页，切过去才渲染。

| 子页面 | 内容 | 高度 |
| --- | --- | --- |
| **总览** | 热力图 + 用量趋势 + 三个关键数字 + 效率卡 + 占比卡 + 次要计数一行 | **恒定 700px** |
| **模型明细** | 全部模型（按费用降序）、"仅显示已调用模型"开关 | 随模型数增长，在面板内滚动 |
| **配置** | 目标货币与汇率、余额查询配置、添加模型 | 203px |

总览里的模型区固定 5 行、超出给一个"还有 N 个模型，查看全部 →"的入口跳到明细页——
所以 5 个模型和 45 个模型的总览高度完全一样（`--models=N` 可验证）。设置面板本身是固定
高度（`min(800px, 100vh − 48px)`），内容在面板内滚动，页面整体布局不会被撑动。

按"用户关心什么"排序，而不是按数据来源排序：

设计理念取自 shell 与 `dsh-context` 的统计页——**计数、占比、趋势是三类不同的东西，
各归其位，互不重复**：

自上而下的顺序就是优先级——**先看结论，再看理由**：

| 顺序 | 卡片 | 承载 | 形态 |
| --- | --- | --- | --- |
| 1 | **关键数字** | 全量计数 | 三张数卡：**本期花费 / 总 Token / 账户余额** |
| 2 | 用量趋势 | 月内怎么变 | 堆叠柱（费用 / Tokens / 工具三种口径） |
| 3 | 开发活跃度 | 一年跨度的强度 | GitHub 风格格子热力图（53 周 × 7 天） |
| 4 | 效率 | 全量计数 | 工具调用 · 失败率 · 每调用均价 · 每调用 Token · 高频工具 |
| 5 | 占比 | 整体的一部分 | 横向条：费用或 Token 在模型间的分配 |

花费与余额放在所有图表**之前**：它是用户最先要看的东西，图表回答的是"为什么"。
这条顺序有闸门断言守着（关键数字的 DOM 位置必须早于趋势图），不会被无声改回去。

**为什么首页不放模型明细**：那是"逐个对象"的清单，属于明细页。首页两处都列模型卡片
就是纯重复（曾经如此）。首页的每条信息都必须是"整体"的——这也正是 `dsh-context`
的原则：*计数不是整体的一部分，所以不画饼图；占比属于另一张卡*。

**两页必须同口径：按"提供服务的模型"分组，而不是按请求里出现的 id。**
一个模型可以有多个历史 id：`deepseek-v4-flash`、`deepseek-v4-flash-vision-exp` 退役后
由 V4.1 Flash 同价继续服务，这些 id 在统计里是同一张卡的组成部分。首版首页按服务模型
合并、明细页按原始 id 分行，于是同一个模型在首页是 ¥183、在明细页变成 ¥8 + ¥131 + ¥44
三个数字——用户会直接判定"统计错了"（线上就是这么反馈的）。现在两页共用同一套分组：

- 明细页一张卡 = 一个服务模型，数字是合并后的；
- 折叠态在调用数后补一句"合并 N 个 id"；
- 展开后逐个列出历史 id 的调用数与 token（`mu-merge-list`），想对账时能看清合计怎么来的；
- 价格配置也挂在服务模型键上，所以退役 id 不会出现"明明有价格却显示未配置"。

代码上这里有个容易踩的坑：`deepseek-flash` 既是服务模型键、又是其中一个原始 id，
同一个字符串在两种口径下答案不同（合并 ¥3 vs 单行 ¥2）。所以**不用字符串去猜意图**，
而是按调用方分成两个函数：`costOf(原始 id)` 走单行（首页逐行汇总才不会重复计数）、
`costOfMerged(服务模型键)` 走合并行。有测试钉住"合并后 15 次调用 / ¥3"。

首页高度因此**不随模型数增长**：11 / 45 / 90 个模型都是 **700px**（实测）。占比卡固定 4 行、
热力图固定 371 格，两者都与模型数无关。

设置面板内容区可用高度是 `800 − 54（头部）− 24（底部内边距）= 722px`，因此 700px 的首页
**一屏放得下、不需要滚动**（这是量出来的，不是估的）。
金额按量级分档显示小数位：`>= ¥0.01` 最多 4 位、更小才到 6 位——一律 6 位会让主数字
变成 `340.992536` 这种读不出来也占宽度的东西，一律 2 位又会把小额项显示成 0。

## 安装

从 GitHub 仓库安装（纯 JS，零构建，即装即用）：

```bash
dsh plugin --profile web add github:AKS1st/model-usage-plugin
dsh web   # 重启 web 服务使 profile 生效
```

本地安装（clone 后直接指向仓库目录）：

```bash
git clone https://github.com/AKS1st/model-usage-plugin.git
dsh plugin --profile web add /path/to/model-usage-plugin
dsh web
```

通过 `dsh plugin`（pnpm 转发）安装到 profile，并自动登记为 bundle 层。卸载：

```bash
dsh plugin --profile web remove model-usage-plugin
```

## 使用

打开 设置 → 模型消耗：

- 顶部：总 Token、账户余额、目标货币与汇率状态
- 每模型卡片：token 明细与费用；点"配置价格"可修改单价与计价货币、启用峰谷定价并设置
  高峰期时间段与高峰价，或点"重置"恢复默认价
- 勾选"仅显示已调用模型"时只展示实际使用过的模型

## 数据与隐私

- 统计、价格、汇率缓存与时间台账保存在 `$DSH_HOME/musage-stats.json`（当前 `version: 6`）
- 价格表以数据文件里的原始模型 id 为键，别名折叠只在查找时发生：这样两个别名
  不会在写入时互相覆盖
- 默认价与高峰窗口的唯一真源是 Host 半部的 `PRESET_PRICES`，随统计快照的 `presets`
  字段下发给浏览器半部；两端不再各存一份，避免"重置"按钮与计费口径漂移
- 统计接口只接受 loopback 同源请求；不要将包含该插件的 WebServer 暴露到公网
- 页面填写的余额 API Key 仅保存在内存，不会写入磁盘；需持久化时请配置 `DEEPSEEK_API_KEY` 环境变量或凭证

## 价格口径

内置价目以官方定价页为准，当前为 2026-09-10 的 DeepSeek V4.1 定价。价格会随官方调价
变化，插件不会联网抓取官方价格，需要更新时改 `src/index.js` 的 `PRESET_PRICES` 并递增
`PRESET_REV`——版本戳递增后，停留在旧默认价的数据会在下次启动时自动升级，而用户自己
填过的单价不受影响。

### 当前官方口径（2026-09-11 抓取）

| | `deepseek-flash`（V4.1-Flash） | `deepseek-v4-pro`（V4-Pro-0813） |
| --- | --- | --- |
| 缓存命中（空闲 / 高峰） | ¥0.02 / ¥0.04 | ¥0.15 / ¥0.30 |
| 缓存未命中（空闲 / 高峰） | ¥1 / ¥2 | ¥4.5 / ¥9.0 |
| 输出（空闲 / 高峰） | ¥4 / ¥8 | ¥13.5 / ¥27.0 |

高峰 = 空闲两倍；窗口为 UTC 周一至周五 01:00–04:00 与 06:00–10:00，其余为空闲。

**兼容 id**：`deepseek-v4-flash`、`deepseek-v4-flash-0731`、`deepseek-v4-flash-vision-exp`
对应模型已下线，请求由 V4.1-Flash 提供服务并按 Flash 价计费，因此它们与 `deepseek-flash`
共用同一价格桶（统计上会被合并，见下文"合并桶会自证"）。

**`deepseek-v4-pro` 是带时点的规则，不是改个数字**：官方在 2026-09-14 12:00 北京时间
（04:00 UTC）之后才把它的请求全部路由到 V4.1 Flash 并按 Flash 价计费。在那之前它仍是独立的
V4-Pro-0813，有独立的价格与统计。预设因此用 `rerouteFrom` / `rerouteTo` 表达这件事，
计费时按当前时间选择费率——**曾经直接把价格预置成 Flash 价，导致 9/14 之前的历史调用
被系统性低估（约 5 倍）**。

### 为什么不会出现"计价为 0"

- **有统计就必须有价**：启动时为"有用量但价格表里没有"的模型补默认预设价（用户显式移除过的除外）。
- **全 0 的价格会被修复**：历史上 `set-price` 在"模型无预设价、用户也没填值"时会写入一条全 0
  的价格，界面上显示成 ¥0（读作免费）。现在这种情况**什么都不写**，保持"未配置价格"；
  启动时也会把已知模型的全 0 条目修正为预设价。
- 因此"未配置价格"与"真的免费"现在是两种可区分的状态。

## 工具调用指标

除了拦截 `llm/stream` 统计 token 与费用，插件还订阅 `session/event` 采集工具调用：

- `tool/call` → `{ turn, step, callId, name, arguments }`
- `tool/result` → `{ turn, step, callId, error?, ... }`

**归因**：工具事件本身不带模型。插件在每次流式调用时记下「会话 → 最近模型」
（`GenerateOptions.sessionId`），工具事件按该会话的最近模型归因；会话未知时归到
`unknown`，计入总量与工具排行但不参与按模型拆分。

**两个易错点**（都有测试钉住）：

1. 一次工具调用会产生 `tool/call` 与 `tool/result` **两个**事件。调用数只在 `tool/call`
   时累加，失败数只在 `tool/result` 带 `error` 时累加——两边都加会把调用数算成两倍。
2. 桶内按工具名的计数有上限（16 个），超出按调用量淘汰；但**调用总数不受影响**，
   因为总量记在按模型的字段里。

与其他指标一样，工具台账**只从本版本上线后开始累积**，不回填历史。

## 先确认版本：面板标题旁的 `vX.Y.Z`

插件改动**必须重启 dsh web 才生效**。界面上标题旁会显示**当前运行中**的版本号，
这就是"我看到的是不是最新代码"的唯一可靠判据：

- 版本号与你刚改的版本不一致 → 重启没生效，不要继续排查功能
- 版本号是新的但某功能仍缺失 → 才是真的看代码

这个标签是踩坑后加的：热力图曾"前台没显示"，根因之一就是重启没生效，
而当时界面上没有任何线索能区分"代码没加载"和"功能有 bug"。

## 开发活跃度热力图

53 周 × 7 天的 GitHub 风格格子，当天用得越多颜色越深（在 **Tokens / 工具调用** 之间切换）。

**为什么给它单独一条台账**：明细时间台账（`dayBuckets`）每天存着逐模型与逐工具的明细，
铺 371 个格子会让 payload 与磁盘都膨胀一个数量级。热力图只需要一个标量，所以另立
`heatBuckets`——**每天两个数**（tokens、工具调用），保留 371 天并只下发有活动的日子。
实测满一年 `heatSeries` 只有 **13.4 KB**（含它之后整份快照 20.4 KB）。

强度按**相对当期峰值**分四档（25% / 50% / 75%），而不是分位数——分位数在稀疏数据上会给出
反直觉的深色格子（只有一天有数据也能染成最深）。格子色由 `brand-primary` 与主题底色用
`color-mix` 混合派生，深浅主题都跟随，不写死色值。

格子尺寸随容器宽度自适应（4–11px），窄栏不会溢出。悬停任意格子弹出该日明细（复用趋势图
那套与 shell 一致的气泡样式与定位）。

### 历史回填

时间台账只从本版本上线后开始累积，但**之前的用量完整存在于会话日志里**。插件启动时会通过
`ctx.sessionQuery`（base 组合已挂载；`openAt: never` 下精确读仍可用，SQLite 从不打开）
读一次历史，把台账里**还没有的日子**补上，并在热力图卡上显示"已回填 N 天历史"。

三条规则缺一不可（都有测试钉住）：

1. **只填缺失的日子**。已存在的日子（含今天）一律不动——因此不会与实时采集重复计数。
2. **只统计本会话自有事件**。`readSession()` 返回的日志带 `inheritedEventCount`：fork 出来的
   会话继承父会话的事件，不切掉这段就会把同一批用量算两次。
3. **有时间预算（30 秒），超时不写完成标记**，下次启动继续。几百个会话可以分几次跑完，
   且不会阻塞启动。

单次会话读取失败（损坏 / 已清理）会被跳过，不中断整轮回填；部署未挂载该服务时优雅降级为
`unavailable`，不影响实时采集。

**必须用延迟注入拿服务**。`session-query-sqlite` 虽然挂在组合里，但 `apply` 执行时该服务
可能**还没注册**——直接 `ctx.get('sessionQuery')` 会拿到 `undefined`，回填就静默不跑
（线上首版正是如此：卡上没有任何历史，状态停在 `unavailable`）。正确写法：

```js
ctx.inject(['sessionQuery'], (scoped) => { runBackfill(scoped.sessionQuery) })
```

回调在依赖可用后触发；服务始终不存在时回调不触发，插件不受影响。这一点有专门的回归测试
（"waits for a service that appears after apply"）。

**免重启的手动重跑**：向现有路由 POST `{ "action": "backfill" }` 即可立刻重跑一轮，
返回 `{ok, state, days, sessions}`；服务缺失时给出明确原因而不是静默无事发生。

#### 一轮不够：重试、唤醒与完成标记

线上踩过两次坑，都被测试钉住：

- **启动瞬间语料可能是空的**。`listSessions()` 在刚启动时返回 0，几分钟后才有 120+ 条。
  首版把"扫了 0 个会话"当成"回填完成"，于是热力图永远空白。现在空语料记 `empty`，
  **绝不写完成标记**，并按 20 秒间隔重试（最多 15 次，约 5 分钟）。
- **定时窗口仍然可能不够长**。所以只要有任何真实会话事件到达（说明语料确实存在了），
  就**唤醒一次**补跑（`kickBackfill`）。唤醒只发生一次，且不新增重试链，
  避免每个事件都触发整库重扫。
- **完成标记用递增版本号**（`heatBackfillRev`）而不是布尔。旧版本误写的
  `heatBackfilled: true` 因此自然失效，会重跑一轮——否则坏标记会让历史永远补不上。
- 重试是幂等的（只填缺失的日子），因此"多跑一轮"永远安全。

`ctx.interval` 返回的是 **disposer 函数**而不是 timer id：停掉定时器必须调用它，
用 `clearInterval` 无效（会退化成无限重试）。这是实际发生过的 bug，已修。
>
> **账为空时这张卡仍然渲染**（铺满格子 + 一句"从本版本开始累积"的说明），而不是整张消失。
> 早期版本写成"有数据才渲染"，于是新装或刚重启时看起来像功能不存在。老版本 host 不提供
> 该字段时则不渲染空壳——两者语义不同，代码里也分开处理。

## 柱数上限与密度

趋势图的柱数是**有硬上限**的，不会随时间变得越来越密：

| 视图 | 数据来源上限 | 图上柱数 |
| --- | --- | --- |
| 按天 | host 只下发最近 45 天 | 上限 30 根 |
| 按小时 | host 只保留 26 小时 | 上限 26 根 |

用满 30 天后柱数不再增长。柱是**靠左排列的定宽块**（不是 `flex:1` 均分整行）：
数据点少时不会被拉伸铺满 —— 5 个数据点时柱群只占 97px / 588px 绘图区。

单柱宽度限制在 12–18px，因此窄栏会自动少画几根（612px 内容区 30 根 → 360px 约 25 根），
而不是把柱子压成读不出形状的细线。没有 `ResizeObserver` 时用保守默认宽度，不影响正确性。

> 测量工具里的柱数始终显示上限值——因为 `preview` 的 markup 在 jsdom 里生成，而 jsdom
> 没有排版引擎。真实的宽度自适应由 `tests/panel.test.mjs` 用 stub 覆盖（612px→30 根、
> 360px→22 根、无 observer→30 根）。

## 悬停浮窗

鼠标移到某根柱上会弹出明细气泡：时段、该时段总量、调用/失败数，以及各模型的用量。

- **样式取自 shell** 的 `ui-primitives/Tooltip`：深色气泡面（`--dsw-alias-tooltip-bg`）、
  固定浅色前景（`--dsw-static-neutral-bluish-*`）、8px 圆角、150ms 淡入
  （尊重 `prefers-reduced-motion`）。
- **`position: fixed`**，用柱子当时的视口坐标定位、水平夹取在视口内、上方空间不足时翻到
  柱子下方。因此它**允许越出图表**——那是气泡的正常行为。
- **不改变布局**：摘要行常驻（固定为"最新时段"），浮窗不占布局空间，所以悬停前后
  页面高度完全一致（闸门会实测比对）。

**约束该加在柱子上，不是加在气泡上**：柱子必须留在绘图区内（定宽靠左块 + 百分比高度）；
气泡只需留在视口内。曾经把两者搞反过——既把气泡限制在绘图区里（样式也换了非气泡的
浅色面），又没有防住柱子纵向溢出。

## 图表的四条硬约束

1. **明细不浮在图上**。悬停/默认时段的明细是图**上方**一条固定高度（18px）的信息行，
   不是绝对定位的浮层。浮层要么盖住最高的柱子、要么越过图表底边——曾经就是这么溢出的，
   而固定高度在数学上不可能溢出。
2. **合并桶会自证**。多个 id 由同一模型服务、按同一价格计费时（Flash 家族），统计会被
   合并成一个桶。桶名后带 `+N` 标记，悬停列出被合并的 id——否则"刚启用的模型怎么花了
   ¥180"这类误解无法从界面上澄清。反过来，**当前是独立模型的 id 绝不合并**：
   `deepseek-v4-pro` 在改路由之前有自己的价格与统计，把它并进 Flash 会同时错算金额和统计。
3. **图例合计与图上的窗口同口径**。柱只画最近 30 天（小时视图全部），图例就按这 30 天
   重算；早期版本图例按全部台账天数累加，数字与占比都跟着错。
3. **柱高只用百分比，不传像素**。曾用 `chartHeight = 132` 在 JS 里算 px，而 CSS 容器
   后来被改窄到 86px——满高的柱子就向上戳出柱区 46px，**且只比左右边界的检查报"无溢出"**。
   百分比高度让 JS 与 CSS 无法漂移，最小可见高度交给 CSS 的 `min-height`。
4. **悬停不改变布局**。摘要行常驻、浮窗 `fixed` 不占空间；真实排版检查会比对悬停前后的
   页面高度。

## 控件样式口径

面板与 shell 同处一个设置面板，控件样式必须取 shell 的口径，否则会像另一套控件。
本插件对齐的是 `@deepseek-ai/dsh-client-ui-primitives` 的 Button 与 settings-models 的 `.input`：

| 控件 | 口径 |
| --- | --- |
| 普通按钮 | `.sm` 胶囊 + `.outline`：`height 28px` / `radius 14px` / `0.5px solid --dsw-alias-border-l3` |
| 按钮 hover / active | `--dsw-alias-interactive-bg-hover` / `--dsw-alias-interactive-bg-active` |
| 选中按钮 | `--dsw-alias-button-primary-fill` + 前景 `--dsw-alias-label-primary-foreground` |
| 输入框 / 下拉 | `height 28px` / `radius 8px` / `0.5px solid --dsw-alias-border-l4` / `--dsw-alias-bg-layer-1` |
| focus | 只换 `border-color: --dsw-alias-brand-primary`，不加 outline |
| 标签页 | 幽灵按钮的 hover/active 底色 + 选中态下划线 |

`npm run verify` 的主题一致性检查会拒绝手写边框宽度、颜色字面量与过小的控件圆角——
这类缺陷正是"按钮看起来和主题不符"的来源。


两条硬约束，都是踩过坑才写进来的：

1. **每个子页面都重新渲染后再截图**。`--shot` 曾经只给"已存在的 HTML"拍照
   （`if (!existsSync(html)) continue`），于是配置页的截图其实是几十分钟前的产物——
   截图看起来是新的，内容却是旧代码，比没有截图更糟。
2. **窗口高度按整页实际高度给**（先 `--dump-dom` 读回布局报告），固定 1400 会在大片空白
   下面拍半屏底色，贴进 README 又难看又像布局坏了。

旧截图必须删掉而不是留着：布局改过之后，过时的图会让读者以为界面还是那样。
`docs/` 下不在清单里的图片会被脚本清理；文件名保持稳定（不带日期/版本），
否则每次发布都会新增一张其实是同一张图的"历史"。

改布局前先**看到**渲染结果，而不是靠想象：

```bash
npm run preview           # 生成 .verify-home/preview-{light,dark}.html（真实组件 + 真实 CSS + 真实主题令牌）
npm run preview:shot      # 再截图成 PNG（每个子页面重渲染后再拍，需要 google-chrome）
npm run preview:measure   # 用浏览器真实排版量出各区块高度、横向溢出与纵向越界
npm run preview:measure -- --width=420   # 换宽度（例如模拟侧栏窄栏）
npm run preview:measure -- --tab=models  # 指定子页面（overview / models / config）
npm run preview:measure -- --models=40   # 指定模型数量，用于验证总览恒定高度
```

预览用**真实组件**（jsdom 挂载 + 真实数据态），CSS 取自客户端 apply 注入的 `<style>`，
主题令牌内联 harness 的 `design-platform.css`，所以配色与线上一致。它不启动、不重启
dsh web，也不写任何真实 profile。

`preview:measure` 会打印页面总高、各区块高度占比、配置区是否收起、柱数与柱群占用宽度、
以及横向溢出与纵向越界。`--hover=N` 可模拟悬停第 N 根柱（浮窗只在悬停时存在，不这样
就量不到它）。布局
问题（某块吃掉半屏、窄栏溢出）因此变成可度量的事实。当前基线（内容区 612px）：

| 子页面 | 页面总高 | 模型数 45 时 |
| --- | ---: | ---: |
| 总览 | 700px | **700px（不变）** |
| 模型明细 | 806px（默认 11 个模型） | 3162px（45 个模型）→ 在面板内滚动 |
| 配置 | 203px | 不变 |

612 / 480 / 420 / 360px 四档宽度均无横向溢出。

这个工具已经抓到过两类真问题：一个会直接崩浏览器的 React Hooks 顺序违规
（`useState` 放在 `if (view === null) return` 之后），以及趋势卡图例按"全部台账天数"
累加、而柱只画最近 30 天的**口径不一致**。

## 测试与验证

```bash
npm test      # 单元测试
npm run verify   # 上线前闸门：不启动、不重启 dsh web
```

### 为什么需要 `npm run verify`

插件装进 profile 后要重启 dsh web 才生效；如果插件本身有问题，重启会把 Web 进程挂死。
`npm run verify` 在**不触碰正在运行进程**的前提下跑九项检查，任何一项失败都明确打印
"不要重启"：

| 检查 | 抓什么 |
| --- | --- |
| 源文件语法 | `node --check`，两个半部加路由安全模块 |
| Host 生命周期 | 真实 `apply()`；导出契约完整；`dispose` 路径不抛错 |
| 主题一致性 | 按钮 / 输入框 / 选中态只用 `--dsw-alias-*` 令牌；禁止手写边框宽度、颜色字面量、过小的控件圆角 |
| Client 注册与回收 | `window.__ModuleLoader__.load()` 契约；注册到 `settings.section`；zh/en 字典 key 对称；effect disposer 可回收 |
| Client 组件渲染 | jsdom 真实挂载 + 数据态渲染：模型名出现、图表真的画出来（趋势卡/堆叠段/花费条/构成条）、设计意图成立（已移除环形图、默认费用口径、卡片默认收起）、文本无 NaN/Infinity/undefined |
| profile 组合树 | `dsh --profile web --dump-config` 能解析且包含本插件行 |
| 价格与迁移路径 | 用 `$DSH_HOME/musage-stats.json` 的真实副本跑一次，校验版本升级、官方单价、UTC 工作日窗口，以及所有 DeepSeek 模型都能计费 |
| 真实排版不越界 | 用 Chrome 实测首页的**默认态与悬停浮窗态**：非固定定位元素不得越出容器上下/左右边界；浮窗必须在视口内且确实渲染；**悬停前后页面高度必须一致**；柱必须是靠左的定宽块。jsdom 没有排版引擎，语法与渲染检查都看不见这类缺陷。同一项还核对 **README 里写下的实测高度**（总览 / 90 个模型 / 配置页）与当前代码一致——文档写着 707px 而界面已经是 700px，比没有文档更误导 |
| 单元测试 | `npm test` 全绿 |

注意 `--dump-config` **只解析组合树、不加载插件模块**——它挡不住语法错误，所以语法与渲染
必须由前面几项负责，两者不可互相替代。

服务面检查用临时目录，不会写入真实 profile；`--real-home` 只影响读取来源，写入始终在临时目录。
